# 量化实验报告

> 实验对象：端侧账单识别模型（拍照 / 截图记账核心能力）
>
> 结论速览：在 204 图（去重 200 图 / 965 笔真值交易）标注集上按图划分 160 训练 / 40 留出测试，模型六轮迭代使测试集整笔交易端到端 F1 从 **0.555 提升到 0.753**（完全命中 109 → 117 → 144 → 151 → **163** / 226 笔；v4 = 块特征 23→37 维 + 跨组去重三元化 + 置信度阈值 0.6→0.8；v5 = 金额抽取强化 + 后处理结构改造；v6 = 列表页行对齐商家覆盖），端云混合策略 F1 达 **0.948**（超过全云端基线 0.909），纯端侧金额 / 商家 / 时间分字段命中率为 **86.3% / 83.0% / 79.5%**，Python 训练侧与 ArkTS 端侧推理**逐位一致**（200 图 / 7,696 OCR 块 / 37 维特征 / 900 笔通过 parity 校验）。

## 1. 实验目的

1. 验证「端侧 OCR + 自训练小模型」在真机离线条件下识别小票 / 支付截图 / 订单截图的可行性；
2. 用真实用户数据迭代模型并量化每次迭代的收益；
3. 保证 Python（训练）与 ArkTS（真机推理）两端特征提取与预测完全一致。

## 2. 数据集

| 项 | 数值 |
| -- | ---- |
| 图片数 | 204 张（去重后 200 张参与训练与评估） |
| 真值交易笔数 | 965 笔（200 图合计；去重丢弃 4 图） |
| 类型构成 | 线下购物小票、支付成功截图（微信 / 支付宝）、外卖 / 电商订单截图 |
| 标签字段 | 金额（元）、商家、支付时间、收支类型、分类 |
| 标注方式 | 用户在确认页人工核对入账，人工确认结果作为真值标签 |
| 脱敏 | 样本仅含 OCR 文本块（相对坐标）与结构化字段，不含图片本身 |

数据集随版本累积：v1（2026-10-21 重训，79 图）→ v2（172 图）→ v3（204 图，本报告基线）。

## 4. 训练方法

1. **样本构造**：每张样本 = 图片宽高 + 端侧 OCR 文本块（相对坐标）+ 用户确认的真值交易；OCR 块与真值交易经**匹配算法**对齐（金额容差 0.011 元、商家相似度阈值 0.62、分类阈值 0.90 等，见 `ml_tools/config.json`）。
2. **特征**：OCR 文本的金额 / 商家 / 时间 / 位置等特征（v4 起块特征 37 维：23 维基础特征 + 14 维 append-only 追加的标签关键词桶 / 千分位 / 粘连小数 / 数字与冒号统计），训练两个子模型：
   - **块级分类**：判断每个 OCR 文本块属于金额 / 商家 / 时间 / 其他（HistGradientBoosting）；
   - **配对决策**：候选块与交易字段的配对打分（DecisionTree）。
3. **超参选择**：网格搜索 **108 组**超参组合，按端到端 F1 选优：
   - HGB：`max_depth=4`，`max_iter=300`，`learning_rate=0.08`
   - 配对树：`max_depth=8`，`min_samples_leaf=8`
4. **导出与部署**：导出为 JSON 权重 → 内置 `rawfile/bill_model.json` → 端侧 ArkTS 推理引擎加载，与端侧 OCR 输出衔接成 `LocalBillModelRecognizer`。

## 5. 评价指标与结果

**评估协议**：200 图按图随机划分 160 训练 / 40 测试（种子固定），测试集真值 226 笔，与训练图无重叠，杜绝「同图泄漏」；v2 / v3 两代模型在同一测试划分上对比。匹配规则与训练一致：金额容差 ±0.011 元，商家模糊匹配分 ≥ 0.7。

### 5.1 模型迭代（整笔交易级）

| 指标 | 定义 | v2（172 图训练） | v3（204 图，23 维特征） | v4（204 图，37 维特征 + 三元去重） | v5（204 图，金额抽取强化 + 后处理改造） | v6（204 图，行对齐商家覆盖） |
| ---- | ---- | ---------------- | ---------------------- | -------------------------------- | -------------------------------------- | ---------------------------- |
| 整笔交易命中 | 金额容差内且商家匹配（贪心一对一） | 109 / 226 | 117 / 226 | 144 / 226 | 151 / 226 | **163 / 226** |
| 端到端 F1 | 整笔交易级精确率 / 召回率调和平均 | 0.555 | 0.584 | 0.673 | 0.699 | **0.753** |

> v4 三项改动：① 块特征 23→37 维（append-only 追加 14 维标签关键词桶 / 千分位 / 粘连小数 / 数字与冒号统计，两端同步实现）；② 跨组去重从「金额+商家」二元改为「金额+商家+时间」三元（同额同商家的多笔交易不再互相吞掉，真值里 41 笔为同额多笔）；③ 端云混合置信度阈值 0.6→0.8（见 5.2 订正）。
>
> v5 两部分改动：① **金额抽取强化**——千分位粘连归一（`1,234.56` OCR 粘成 `1234.56` 时还原）、前导零 / 0 元拒绝、标签关键词加权（实付 / 实收类 +2，优惠 / 余额类 −3）、金额标签分级（实付 / 实收 > 合计 / 金额 > 无标签，组内只保留最高级别候选，优惠 / 余额块直接丢弃）；② **后处理结构改造**——金额预测块各自独立成候选（多笔并组不再丢笔）、商家四级回退（组内商家预测块 → 标签词块 → CJK 最多块 → 跨组商家块；跨组属猜测，conf ×0.8 不参与加成，否则低质量图混过阈值、混合 F1 反降至 0.845）、时间图级共享解析（去掉全局占用表，头图日期可服务多笔）、三元去重。5 折成对复核：v5 五折全胜，累计 F1 0.634 → 0.665。
>
> v6 **列表页行对齐商家覆盖（rowmer）**：漏检归因显示 73% 的整笔 miss 源于商家选错，其中多行列表页（支付宝 / 微信 / 银行账单截图）占大头——这类版式日期 / 金额 / 商家分列，阅读序邻近的商家往往是别行的通用商家。改法：现行商家块与金额块不同行时，在与金额块同一横带（垂直重叠 ≥ 0.4×min(块高) 或中心距 ≤ 0.5×中位块高）里选商家样候选覆盖，按 P_mer + 0.03×min(CJK 数, 12) 打分取最优；**双门控防详情页回归**——仅列式布局（≥4 个金额预测块 x 中心聚同列 ±0.07）或候选本身强商家（P_mer ≥ 0.35）时启用，且候选须过文本门（CJK ≥ 4 或拉丁 ≥ 5 或 P_mer ≥ 0.35）、排除大写金额词（壹贰叁… / 圆整 / 元整 / 人民币）。测试集 +12 修复 / 0 回归（F1 0.699 → 0.753，商家命中率 77.2% → 83.0%）；5 折成对复核 5/5 非负（Δ +0.042 / +0.147 / +0.097 / +0.033 / 0.000），累计 F1 0.665 → 0.733。

### 5.2 分字段准确率（v6，测试集 226 笔真值）

| 字段 / 指标 | 端侧模型（离线） | 云端多模态（基线） | 端云混合（置信度 < 0.8 整图回退） |
| ---------- | ---------------- | ------------------ | -------------------------------- |
| 金额命中 | 195 / 226 = **86.3%** | 211 / 226 = 93.4% | 216 / 226 = 95.6% |
| 商家命中 | 161 / 194 = **83.0%** | 199 / 210 = 94.8% | 209 / 215 = 97.2% |
| 时间命中（±2 分钟） | 155 / 195 = **79.5%** | 201 / 211 = 95.3% | 198 / 216 = 91.7% |
| 整笔命中 | 163 / 226 | 200 / 226 | 210 / 226 |
| 精确率 / 召回率 | 0.787 / 0.721 | 0.935 / 0.885 | 0.968 / 0.929 |
| 端到端 F1 | **0.753** | 0.909 | **0.948** |

> v3 的分字段数字（71.2% / 71.9% / 75.8%，混合 F1 0.704）见 git 历史。

> 分母说明：金额命中的分母为全部真值（226）；商家 / 时间在「金额配对成功」的子集上评估（真值商家非空 / 真值含支付时间）。
>
> **云端多模态基线** = 多模态识别的原始输出（用户确认前）对同一人工确认真值的命中，即衡量用户在确认页的修正率；端侧模型在同一真值上评估，两者可比。
>
> **端侧的定位**：离线、免流量、隐私不出设备，77%~86% 的字段命中率足够支撑「先自动填、确认页人工修正」的产品形态；需要更高精度时依赖混合策略或云端。
>
> **混合策略的发现（v3 结论订正）**：v3 曾判断「端侧错误多为高置信度错误、置信度信号区分力不足」——**该判断不成立**：置信度实测判别力良好（ROC AUC ≈ 0.885，conf ≥ 0.9 的预测正确率 0.903，而 0.7~0.8 区间仅 0.179），真正的问题是 **0.6 的阈值定得过低**（40 图仅 6 图触发云端回退），导致 v3 的「混合收益有限」（F1 0.704）实为**阈值未调优**。v4 将阈值扫描定至 0.8 后混合 F1 升至 0.946、反超全云端基线 0.909；v5 后处理改造后复扫 0.8 仍最优，v6 行对齐覆盖后第三次复扫仍 0.8（0.6 / 0.7 / 0.75 / 0.8 / 0.85 / 0.9 → F1 0.805 / 0.918 / 0.930 / **0.948** / 0.944 / 0.889，回退 5 / 11 / 14 / 23 / 25 / 31 图）——高置信图的端侧结果质量本就不差于云端，混合策略让云端只在真正难的图上出手（23/40 图回退，代价是流量 / 延迟 / 隐私，需要离线的场景仍可纯端侧 0.753 兜底）。

### 5.3 两端一致性（parity）

模型迭代与部署必须保证真机行为与训练侧完全一致，parity 校验逐位比对 Python 与 ArkTS 的输出：

| 校验范围 | 结果 |
| -------- | ---- |
| 200 张图 | 通过 |
| 7,696 个 OCR 块分类 / 配对 | 逐位一致 |
| 900 笔交易抽取 | 逐位一致 |

### 5.4 工程稳定性指标（定性）

- 端侧 OCR 串行队列增加 **30s 看门狗**，防止底层静默挂起导致识别卡死；
- 云端识别失败自动降级端侧（弱网可用），批量识别单图失败不影响其他图；
- 入账防重入（双击保护）与金额上限钳制（¥9,999,999.99）。

## 7. 复现步骤

训练工具链位于开发机 `ml_tools/`（独立于应用仓库，属开发期工具，不随应用分发）：

```bash
# 1. 标注：OCR 块与人工确认交易对齐，生成训练样本
python label_samples.py

# 2. 训练：网格搜索超参，训练并导出 bill_model.json
python train_model.py

# 3. 一致性：导出 parity fixture，ArkTS 侧逐位比对
python export_parity_fixture.py
node parity/run_parity.ts

# 4. 分字段评估：金额 / 商家 / 时间 / 整笔，端侧 vs 云端基线 vs 端云混合
python eval_fields.py

# 5. 阈值扫描：端云混合置信度阈值定值（Config.ets RECOGNIZE_CONFIDENCE_THRESHOLD）
python _scan_threshold.py
```

将产出的 `bill_model.json` 放入 `entry/src/main/resources/rawfile/`，`devecocli build` 后真机运行。

## 8. 局限与后续

1. **样本量**：204 图（去重 200 图）规模仍小，40 图留出集指标波动大（5 折交叉验证下各折 F1 0.49~0.76），单折 <±0.03 的差异可能是划分噪声，后续改动验收建议用 5 折复核；
2. **耗时**：端侧识别秒级、云端数秒（依赖网络），未做正式计时实验，以演示视频现场表现为准；
3. **复杂版式**：多笔交易、竖排、折叠小票仍是难点，靠确认页人工修正兜底并回流为训练数据；
4. **后续**：后处理结构性改进中「商家以金额块为锚点选取」「时间块图级共享」已在 v5 落地，「列表页行对齐商家覆盖」已在 v6 落地；漏检归因显示剩余缺口 73% 在商家、17% 在块分类（Oracle 复测：块分类完美时 F1 上限 0.851，商家 OCR 缺失部分端侧不可修，见[端侧模型升级研究](./端侧模型升级研究.md)）；确认页补「漏检回传」入口解决漏检样本系统性缺失；持续累积样本迭代模型。
