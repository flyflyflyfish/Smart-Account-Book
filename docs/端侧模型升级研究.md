# 端侧模型升级研究

> 研究对象：端侧账单识别模型（`bill_model.json` + `BillModelCore.ets`）的升级空间与发行路径
>
> 结论速览：模型侧升级的天花板被后处理封死——块分类+分组全换真值，现行抽取/去重逻辑下端到端 F1 也只能到 **0.773**（基线 0.584）；分组模型升级**零收益**（Oracle 实验 0.579 vs 0.584）；特征增强（23 维→37 维）是真实但微小的增量（**+0.011**，与 P0 去重修复叠加后 0.662→0.673）。**建议特征增强与 P0 后处理修复打包成同一个发版，不为模型单独发版。**
>
> **落地状态（2026-11-04）**：第 2、3 条建议已实施——37 维特征（两端同步）、三元去重、置信度阈值 0.6→0.8 已合入，并追加 v5 金额抽取强化与后处理结构改造（金额块独立候选 / 商家四级回退 / 时间图级共享解析）、v6 列表页行对齐商家覆盖（漏检归因 73% 在商家后定向修复：金额块同行商家样候选覆盖 + 列式布局门 + 文本门），重训后纯端侧 F1 **0.753**（v6 5 折成对复核 5/5 非负，累计 0.665 → 0.733）、混合 F1 **0.948**（超全云端基线 0.909），parity 200 图 / 7,696 块 / 900 笔逐位一致。本文研究数据（0.584 基线、Oracle 上限）为 v3 历史快照；Oracle 复测（v5 后处理口径）：块分类完美时上限 0.851、分组 oracle 无增益（0.696）、商家 14 笔 OCR 缺失端侧不可修。
>
> **v7 探索（2026-11-04，均未落地）**：针对 v6 后剩余缺口（63 miss = 商家 43 / 块分类 13 / 金额不在 OCR 7）的三个方向经成对复核全部放弃——金额块抢救（noise→amount 重标）F1 0.730~0.745 劣于基线 0.753（订单页行项目 FP 洪泛）；时间垂直最近仅 +1 时间命中、e2e 不动；金额列对齐特征（37→39 维）5 折 +0.002 噪声级、留出 -0.003，未达「5/5 折非负」门槛。详见第 6 节。**后处理与当前特征空间的边际收益已耗尽，模型侧下一步唯一现实方向是样本量翻倍后重训。**

## 1. 研究动机

前期误差归因（同一 200 图标注集 / 40 图留出 / 226 笔真值）显示：块分类模型本身已够准（amount P/R 0.902/0.932，merchant 0.895/0.798，time 0.954/0.920，noise 0.931/0.954），准确率主要被交割后处理（全局同额同商家去重、0.6 置信度阈值、商家回退策略）吃掉。本研究用 Oracle 上限实验定量回答：**换更准的模型（特征/结构/超参）最多还能买回多少，是否值得为它单独发版。**

## 2. 实验设计

同一 40 图留出集（seed=20261006），逐项替换流水线环节为「真值 Oracle」，量化各环节单独升级的绝对上限：

| 实验 | 替换环节 | 回答的问题 |
| ---- | -------- | ---------- |
| A. baseline | 无（现行发行配置） | 复现基线 |
| B. oracle-labels | 块分类 → 真值标签 | 块分类模型再准，e2e 最多涨多少 |
| C. oracle-grouping | 相邻分组 → 真值 txnId | 分组/配对模型升级的上限 |
| D. oracle-both | 两者都 → 真值 | 现行抽取/去重/商家选择后处理的硬上限 |
| E. feat-augmented | 23 维 → 37 维（追加 14 维关键词桶/千分位/粘连小数/digit 桶等） | P2「补特征重训」的实际收益 |
| F. hparam 粗扫 | depth 3~6 / iter 300~500 / lr 0.08~0.12 | 调参还有没有空间 |

另做 5 折按图交叉验证（每折 160 训练 / 40 测试）复核 E 的稳定性，以及「去重模式 global/triple × 特征 base/aug」叠加矩阵。

## 3. 结果

### 3.1 Oracle 上限（40 图留出集）

| 路径 | e2e F1 | 相对基线 |
| ---- | ------ | -------- |
| A. 现行发行模型 | 0.584 | — |
| B. 块分类 = 真值 | 0.747 | +0.163（任何块分类升级的绝对上限） |
| C. 分组 = 真值 | **0.579** | **-0.005：分组模型升级零收益** |
| D. 块分类 + 分组 = 真值 | **0.773** | 现行后处理下纯端侧硬上限 |
| E. 特征增强（37 维） | 0.595 | +0.011 |
| F. 超参粗扫 5 组 | 0.547~0.584 | 现行配置已是扫描最优 |

关键读数：

1. **纯模型升级不改后处理，最多 0.584 → 0.773**，且这是「完美分类器」的理论值；实际可达的特征增强只有 +0.011。混合策略调阈值（0.8~0.9 时 F1 0.878/0.893，云端兜底）已**超过**该上限。
2. **分组/pair tree 不是瓶颈**：Oracle-grouping 反而 -0.005——标签错在哪组就跟到哪，换更好的配对模型无济于事。分组问题的正确解法是 P1 的结构化改造（金额块独立成候选 + 全局分配），不是换模型。
3. **特征增强真实但微小**：merchant 块召回 +3pt（0.798→0.828），amount/time ±0.005 量级；5 折累计 e2e 0.594→0.602（+0.008），方向稳定。

### 3.2 与 P0 去重修复的叠加（同划分）

| 去重模式 | base（23 维） | aug（37 维） |
| -------- | ------------- | ------------ |
| global（现行） | 0.584 | 0.595 |
| triple（金额+商家+时间，P0-1） | 0.662 | **0.673** |

特征增强与后处理修复**叠加无损耗**（恒定 +0.011）。

### 3.3 5 折交叉验证（特征增强稳定性）

| 折 | base F1 | aug F1 |
| -- | ------- | ------ |
| 1 | 0.759 | 0.749 |
| 2 | 0.491 | 0.512 |
| 3 | 0.573 | 0.574 |
| 4 | 0.491 | 0.525 |
| 5 | 0.662 | 0.651 |
| **累计** | **0.594** | **0.602** |

各折 F1 从 0.49 到 0.76 波动——**40 图留出集的绝对值不可靠，任何 <±0.03 的单折差异都可能是划分噪声**；发版验收应使用 5 折交叉验证。

## 4. 结论与建议

按「收益 / 改动量 / 发版成本」排序：

1. **P0 后处理修复优先**（纯端侧代码，不动训练侧、不破坏 parity）：去重 triple 化（0.584→0.662）、置信度阈值 0.6→0.8~0.9（混合 F1 0.704→0.878/0.893）、金额正则归一。
2. **P2 特征增强搭车同发**：+0.011 真实但微小，不值得单独走发版流程；与 P0 打包后纯端侧预期 0.67+、混合策略 0.89 上下。推荐 append-only 方案：14 维新特征全部追加在 23 维之后，不动 `feats[0]/feats[1]`（pair 特征索引安全），两端改动最小。
3. **分组模型与超参调优不做**：Oracle 实验证明零收益。
4. **样本回流（P2 数据侧）继续**：漏检样本系统性缺失是模型侧唯一值得投入的方向，但收益要到样本量翻倍后才显现。

## 5. 发行版升级路径

模型升级的完整链路（每步均已核实过现状）：

```bash
# 1. 训练（改特征需同步改 train_model.py 的 block_features）
python ml_tools/train_model.py
# 2. 同步端侧：BillModelCore.ets 的 blockFeatures 与训练侧逐位一致
# 3. parity 校验（ml_tools/parity/BillModelCore.ts 与 .ets 须逐字节一致）
python ml_tools/export_parity_fixture.py
node ml_tools/parity/run_parity.ts
# 4. 部署：model.json → entry/src/main/resources/rawfile/bill_model.json（随包内置约 2.7MB，无 OTA 通道）
# 5. devecocli build → 签名 → 发版
```

现状核实（2026-11-04，v7 收尾复核）：`rawfile/bill_model.json` 与 `ml_tools/output/model.json` SHA256 一致（78287D4F…，meta 与权重同步，`meta.endToEnd` 为 v6 实测 163/0.753）；`parity/BillModelCore.ts` 与端侧 `.ets` 逐字节一致。

**待办（正式版发行前）**：签名与上架流程尚未研究——发布证书 / Profile 配置、AGC 提审材料、模型文件随包的隐私披露口径（识别完全在端侧，模型不联网）需在正式版排期前补齐。

## 6. v7 探索（2026-11-04，三方向均未落地）

v6 收官后对剩余缺口做归因（63 miss = 商家 43 / 块分类 13 / 金额不在 OCR 7；FP 44 笔），据此探索三个方向，全部经 5 折成对复核或逐图 FP 归因后放弃：

### 6.1 金额块抢救（后处理，放弃）

针对 9 笔可救块分类漏检（纯小数/千分位文本块被分到 noise：'209.00'、'4,500.00'、'175.56' 等，x 中心与金额预测块同列 ±0.07），在分组前做 noise→amount 重标（P_amount≥0 + DEC2/千分位 + 列对齐 ≥N 个金额预测块）：

| 配置 | hit | pred | F1 | 对比基线 0.753 |
| ---- | ---- | ---- | ---- | ---- |
| n≥1 | 165 | 226 | 0.730 | -0.023（+19 预测仅 +2 命中） |
| n≥2 | — | 217 | 0.745 | -0.008 |
| 与时间改进叠加 n≥2 | 166 | 218 | 0.748 | -0.005 |

逐图 diff 定位 FP 洪泛：电商订单页每行「商品名 + 实付款」与支付列表结构同构（#45/#49/#50 各 +3~4 预测、#112/#141/#105 全 FP），无更高级金额标签的组无法靠标签筛压制；且被救块 P_amount 低 → conf 低 → 混合模式下整图回退云端，无补偿收益。

### 6.2 时间垂直最近（放弃）

针对 #116 跨交易时间串扰（组内最近时间取到相邻交易），把组内时间改为「组外带日期块按垂直中心距取最近（ring≤8）」：time_hit 139→140（+1），e2e 不动（时间不在 txn_match 判据里，仅经去重三元组间接影响）。单独无发版价值。

### 6.3 金额列对齐特征（37→39 维重训，放弃，代码已回退）

新增 2 维 append-only 特征：金额锚块（squeeze 后含 ¥ 或前导 +-/−）列的 x 中心与右缘中位数，块对齐度 `max(0, 1-|Δ|/0.2)`、`max(0, 1-|Δ|/0.1)`，digit 占比 ≤0.3 的块取 0.5 中性（防误伤商家）：

- **有效面**：5 类目标块翻正（'209.00'/'175.56'/'29.9'/'136.79' 等），#45 订单页挤掉 3 个行项目 FP，#80/#168 各 +1 命中；
- **代价**：重训后商家边界漂移（#156/#107/#58 商家块翻 noise 各 -1 命中），留出集 163→162（F1 0.753→0.750）；
- **5 折成对复核**：4/5 折微正（+0.001~+0.007），fold5 -0.002，累计 0.733→0.735（+0.002）——量级为噪声级（v6 为 +0.068），未达「5/5 折非负」发版门槛，判定不落地。

### 6.4 剩余缺口构成与结论

v6 后不可修池：mer-not-in-ocr 14 笔、OCR 误读（#168/#91 的 '-180'/'8n' 等）、重复真值假 miss（#91/92/116/141 同额同商家多笔）、订单页行项目结构性 FP（#168 11 笔多为 OCR 误读）。**后处理与当前 37 维特征空间的边际收益已耗尽**；块分类上限（Oracle 0.851）与现值 0.753 之间的差距需靠样本量翻倍 + 更强 OCR 解决，端侧代码不再投入。
