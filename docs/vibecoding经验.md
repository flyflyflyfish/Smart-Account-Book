# 大模型辅助开发（vibecoding）经验

> 本文记录团队在本项目中使用大模型的方式、原则与经验。
>
> 内容依据仓库提交历史、PR 描述与本次交付物整理的真实过程撰写；没有留存记录的部分（如早期提示词原文）如实说明，不补写虚构细节。第 5 节个人体会如需署名，由成员本人在本节追加。

## 1. 实际工作流与使用范围

本项目的代码几乎全部由大模型编写，人负责派活、验证和把关。

| 环节 | 使用的工具 | 做什么 |
| ---- | ---------- | ------ |
| 总体分析与提示词起草 | Claude | 先分析整体需求，再起草分步骤的提示词 |
| 编码实现 | DevEco Code（终端 agent）中的 GLM5.3 | 按提示词一块一块实现，几乎所有代码由它完成；选它的原因是在 DevEco Code 里可以免费使用 |
| 验证 | 真机运行 | 人在真机上操作应用，发现问题 |
| 缺陷修复 | 同一个 agent | 人把现象反馈给 agent，由它自己定位并修复 |
| 文档与 CI | 模型起草、人审校后提交 | 11-04 的用户手册、设计与重构报告、量化实验报告、隐私政策、用户协议、CI 配置等均按此流程产出；单元测试位于 `entry/src/ohosTest`，本次交付物整理未改动测试代码，测试补充见 issue #6 |

两名成员均直接向同一仓库提交，人工把关的重点是：需求有没有被理解错、改动范围有没有越界、有没有把未验证的东西当成已完成。

## 2. 工作原则

以下原则来自开题报告：

1. 先给设计约束与接口，再让模型生成实现；
2. 生成的代码必须经过人工审查与测试验证后才能提交；
3. 保留关键提示词和迭代过程，记录"如何用好"的经验。

实际做法是"两段式"：让对话能力强的模型先做整体分析并写好提示词，再把提示词拆成小步骤交给执行 agent，每一步完成后在真机上验证，再进入下一步。

第 3 条执行得并不好：早期分步派活时的原始提示词没有系统留存，只有提交说明里保留了结果和根因。这也是本次补写经验文档时最直接的教训 —— 第 3.3 节因此只能依据提交说明还原案例，无法给出提示词原文。

## 3. 案例

### 3.1 案例记录模板

每个案例按下面四项写，便于展示时讲清楚：

- **目标**：想让模型做什么
- **怎么问的**：关键提示词或给了哪些约束
- **哪里出了问题**：模型的输出错在哪里、是怎么发现的
- **如何纠正**：人工做了什么，最后怎么验证的

### 3.2 案例：课设交付物的准备（2026-11-05，使用 Claude）

这个案例是本次整理交付物时发生的，记录者当时就在场。

- **目标**：对照课设评分表，找出仓库缺口并补齐。
- **做法**：让 Claude 读取仓库的分支、提交、PR、issue、CI、`scripts/` 与 docs 目录，对照评分表逐条核对；再由 Claude 创建 issue、通过分支和 PR 提交改动。
- **发现的问题**（均为实测）：此前 PR 与 issue 均为 0；`scripts/` 下没有部署与 demo 脚本；KPI 文档缺少分配方式，且伍翰彬的行数为空；CONTRIBUTING 中的分支名与实际不符。
- **Claude 自己的验证**：格式检查脚本和运行脚本，在临时 git 仓库中用构造的正反例跑过（行尾空格、Tab、缺换行、CRLF、Markdown 豁免、参数错误、回退逻辑）；伍翰彬的行数通过 GitHub 提交接口逐条核对，与原文档合计一致。
- **没有验证的部分**：CI 在 GitHub 上的实际运行、`pre-commit install` 的真实流程、`devecocli build` 命令本身。Claude 没有 DevEco 环境，也无法运行 HarmonyOS 应用，这些必须由人在真机或 IDE 上确认，PR 描述中已逐项写明。
- **后续发现并修正的问题**：PR #11 的分支是基于 #10 的分支创建的，把 #10 的 3 个提交一起带了进来，PR 里一度显示 6 个改动文件；若先合并 #10 再合并 #11，会产生重复改动冲突。人工将两个分支与 `main` 做了三路比对后，把 #11 重建为直接基于 `main` 的单个提交，只保留 `scripts/run.sh` 与 `scripts/README.md`。这说明"让模型并行开多个分支"时必须检查分支基线，不能只看 PR 页面上的 `mergeable` 标记。
- **必须由人做的部分**：工作量分配比例需由两人协商确认（KPI 文档 3.3 节只依据 git 度量给出建议值，不代为决定）；伍翰彬自己的工作量不能由模型代做，只能由他写测试、开 issue、做评审；真机验证与演示视频也无法由模型完成。
- **体会**：让 Claude 先"审计"再"动手"，比直接让它"补齐所有内容"可靠得多；同时一定要让它写明哪些没验证过。

### 3.3 来自提交历史的案例

下面几处在提交说明中有明确记录。这两个缺陷都是 agent 写出来的，在真机上暴露，由同一个 agent 自己修复。**早期分步提示词的原文未留存，无法复原，以下"怎么问的"只写能从工作流确认的部分，不补写具体措辞。**

1. **真机批量删除必败**（多账本提交）：`RdbPredicates.in` 在真机上抛出参数错误，改为循环单删。
   - 怎么问的：按"两段式"分步派活，先给接口与约束、限定改动文件，再让执行 agent 实现；原始提示词未留存
   - 哪里出了问题：agent 写的实现在真机上报错，静态检查与模拟结果不能代替真机
   - 如何纠正与验证：人在真机上发现并反馈现象，agent 自行定位并修复，改动后在真机上验证
2. **切主题后小组件卡片变棕**（桌面小组件重构提交）：主应用与卡片进程的 preferences 缓存实例互不可见，读写前需要重新加载。
   - 怎么问的：同上，按分步提示词派活；原始提示词未留存
   - 哪里出了问题：跨进程的缓存可见性问题，只有在真机上切换主题才会出现
   - 如何纠正与验证：人在真机上发现并反馈现象，agent 排查出原因并修复，提交说明中记录了根因（跨进程读写前 `removePreferencesFromCache` 重载）
3. **识别后处理的三个方向最终不落地**（v7 收尾提交）：经成对复核，三个方向均无净收益，训练侧代码已回退。
   - 目标与方向：金额块抢救、时间垂直最近、金额列对齐特征，均为针对端侧识别剩余缺口的探索；由模型在实验环节提出，提交说明未记录具体提出者，此处不臆测
   - 怎么复核的：5 折成对复核，并预先设定"5/5 折非负"才允许发版的门槛
   - 实测结果：抢救方向 F1 0.730–0.745，劣于基线 0.753，误检洪泛来自电商订单页的行项目实付款；时间垂直最近仅多命中 1 处、端到端指标不变；列对齐特征 5 折累计仅 +0.002 且 fold5 为负，未达门槛
   - 如何纠正：三个方向全部不落地，训练侧代码回退，模型权重不变（SHA 78287D4F 两端一致），rawfile 模型 meta 与训练产物重新同步；结论写进提交说明：后处理与 37 维特征空间的边际收益已耗尽，剩余缺口在 OCR 侧，样本翻倍重训才是现实方向
   - 这个案例的价值在于"用数据否决了方案"：模型给出的优化方向听起来都合理，但只有预先定好复核口径和发版门槛，才能避免把噪声当收益合进主干

## 4. 经验与坑

以下每条都能在上面的案例或提交历史里找到对应实例。

- **适合交给模型的任务**：目标明确、有清晰接口与可自动验证产物的改动。本次的 `check_format.mjs`、`run.sh`、CI 格式任务都是一次成型，因为能用构造的正反例在本地跑出确定的退出码；反过来，需求含糊或需要跨模块权衡的任务，直接让模型"一口气做完"很容易改飞。
- **最容易翻车的任务**：涉及真机、跨进程、设备特性或较新 API 的逻辑。3.3 的 `RdbPredicates.in` 参数错误和卡片进程 preferences 缓存不可见，静态检查和模拟器都没发现，只有真机能暴露。
- **为什么坚持"两段式"**：先让对话能力强的模型做整体分析、写出分步提示词，再交给执行 agent 逐块实现，每步真机验证。3.2 的交付物整理就是先审计再动手；如果不拆步骤，一次改动会覆盖多个文件，出问题后很难定位是哪一步引入的。
- **模型生成代码最常见的问题**：把"能编译 / 看着合理"当成"能跑"，并对不熟悉的 API 行为做想当然的假设。因此人工审查的重点不是逐行读代码，而是检查改动范围、要求模型给出自测方式，并明确列出它没验证过的部分。
- **为什么验证必须上真机**：HarmonyOS 的跨进程、卡片、签名、AGC 云同步等行为无法在纯 Node 环境复现。本次 PR 描述里逐项写明"未验证：真实环境下的 `devecocli build`"，就是为了不让未验证内容混进已完成清单；这部分最终只能由人在 DevEco Studio 和真机上补上。
- **ArkTS 严格模式这类资料较少的技术栈**：模型的写法容易踩严格模式约束，补救办法是提示词里先给仓库中同类代码作范例、限定只改指定文件，再用 `codelinter` / `devecocli check arkts` 与 CI 兜底，而不是指望模型一次写对。
- **提示词里加什么最有效**：给定接口与设计约束、限定改动文件范围、要求给出自测方式、要求显式列出未验证项。开题报告里的三条原则中，"先给约束"和"必须验证"在实践中收益最大。
- **一定要设可量化的准入门槛**：v7 的"5/5 折非负"就是例子。没有门槛时，+0.002 这种噪声很容易被当成优化合进去；有门槛才能干净地回退。
- **过程记录要当场做**：早期提示词没留存，导致 3.3 只能靠提交说明还原。提交说明写得详细（含数据、根因、回退结论）这次救了场，但更稳妥的做法是把关键提示词随 PR 一起归档。

## 5. 团队共同体会

- 最大的收益不是"少写代码"，而是把人从重复劳动里解放出来，去做只有人能做的事：真机验收、判断方案是否真的有效、决定工作量分配、准备演示。3.2 里"必须由人做的部分"和 v7 的"用数据否决方案"都是这个分工的体现。
- 模型越强，越需要清晰的边界。给它的约束越具体（改哪些文件、怎么算做完、哪些必须人验），产出越可用；反过来，一句"把剩下的都补齐"最容易埋雷 —— #11 分支混入重复提交就是这么来的。
- "能跑"和"能用"之间隔着真机。本项目几乎所有值得写进文档的缺陷，都不是编译错误，而是在真机上才暴露的行为差异。
- 保留"没验证"的声明，比多写一段漂亮结论更重要。评审时看到明确的未验证清单，才知道该把注意力放在哪里。
- 最该改进的是过程留痕：提示词、迭代记录、复核口径如果当场归档，经验文档就不用事后靠提交说明反推。
