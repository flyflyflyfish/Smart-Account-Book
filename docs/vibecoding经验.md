## 2. 工作原则

以下原则来自开题报告：

1. 先给设计约束与接口，再让模型生成实现；
2. 生成的代码必须经过人工审查与测试验证后才能提交；
3. 保留关键提示词和迭代过程，记录"如何用好"的经验。

## 3. 案例

### 3.1 案例记录模板

每个案例按下面四项写，便于展示时讲清楚：

- **目标**：想让模型做什么
- **怎么问的**：关键提示词或给了哪些约束
- **哪里出了问题**：模型的输出错在哪里、是怎么发现的
- **如何纠正**：人工做了什么，最后怎么验证的

### 3.2 案例：课设交付物的准备（2026-11-05）

这是本文唯一一个已写完整的案例，因为记录者当时就在场。

- **目标**：对照课设评分表，找出仓库缺口并补齐。
- **做法**：让模型读取仓库的分支、提交、PR、issue、CI、`scripts/` 与 docs 目录，对照评分表逐条核对；再由模型创建 issue、通过分支和 PR 提交改动。
- **发现的问题**（均为实测）：此前 PR 与 issue 均为 0；`scripts/` 下没有部署与 demo 脚本；KPI 文档缺少分配方式，且伍翰彬的行数为空；CONTRIBUTING 中的分支名与实际不符。
- **模型自己的验证**：格式检查脚本和运行脚本，在临时 git 仓库中用构造的正反例跑过（行尾空格、Tab、缺换行、CRLF、Markdown 豁免、参数错误、回退逻辑）；伍翰彬的行数通过 GitHub 提交接口逐条核对，与原文档合计一致。
- **没有验证的部分**：CI 在 GitHub 上的实际运行、`pre-commit install` 的真实流程、`devecocli build` 命令本身。模型没有 DevEco 环境，也无法跑 HarmonyOS 应用，这些必须由人在真机或 IDE 上确认，PR 描述中已逐项写明。
- **人必须做的部分**：分配结果由两人协商决定，模型没有代填；伍翰彬自己的工作量不能由模型代做，只能由他写测试、开 issue、做评审。
- **体会**：让模型先"审计"再"动手"，比直接让它"补齐所有内容"可靠得多；同时一定要让它写明哪些没验证过。
