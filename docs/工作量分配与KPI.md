# 工作量分配与 KPI

> 团队：潘妍朵、伍翰彬（2 人）
>
> 分配原则：两条主线各自负责——**智能识别与云能力（技术主线）** 与 **产品体验与交付（界面主线）**；条线权重按风险与交付确定，git 度量（提交数 / 变更行 / 贡献者归属）作为客观可复现的佐证，不单独决定权重。

## 1. 分工声明与工作量占比

| 成员 | 主责条线 | 主要交付物 | 工作量占比 |
| ---- | -------- | ---------- | ---------- |
| 潘妍朵 | 智能识别与云能力（技术主线）：端侧模型与识别流水线 · 云端大模型接入 · AGC 端云同步 · 数据层与账本 · CI 与工程脚本 | 六轮模型迭代与 parity 实验报告 · 华为账号云同步 · 多账本与导入导出 · 预算与周期账单 | **65%** |

两名成员均向同一仓库直接提交代码，GitHub 贡献者页面按各自 commit 归属，无「只由一人提交」的情况。

## 2. 权重依据：为什么不按行数分

- **核心风险不对称**：技术主线承担模型训练与端云同步的核心风险——六轮模型迭代、Python/ArkTS 两侧 parity 校验、双向合并与墓碑机制的设计正确性，返工成本远高于界面调整；
- **行数被界面重写放大失真**：小部件双布局重设计等界面改动单次变更可达 826 增 / 793 删，但属于同一需求的反复迭代，行数无法反映需求难度；
- **部分关键工作不产生提交**：真机验收、演示准备、跨进程缺陷定位大量时间不落在 git 历史里，按行数计算会系统性低估界面主线的投入。

综合以上，条线权重定为 **65% : 35%**。

## 4. 提交质量

- 统一 `类型(范围): 详细中文说明` 格式，全文中文不混用；
- 单一职责粒度：一个 commit 一件事（可查 `git log --stat main`）；
- 关键 commit 附量化说明（如准确率、命中数、parity 规模）。

## 5. 度量说明与已知问题

- 行数含自动生成资源的增删，仅作工作量参考，**不作为唯一标准、不单独决定权重**（理由见第 2 节）；
- **已知问题**：git 度量呈现提交比例失衡（115 : 6），部分原因是测试、评审、真机验收类工作缺少 git 留痕，导致度量偏小。改进方向：测试验证、issue、PR 全部走仓库流程留痕，让每类工作可度量（如 #6「补充单元测试」已在 issue 中记录）；
- 代码走查、真机联调验收、演示准备由两名成员共同完成，未计入 git 度量。
