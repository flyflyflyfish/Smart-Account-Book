## 3. 分配依据与原因

### 3.1 为什么不只看代码行数

- 识别子系统的工作包含模型训练、特征设计、实验与 parity 校验，产出体现在准确率提升和实验报告上，不完全等价于代码行数；
- UI 工作的行数受界面重写影响较大（见 2.3 中 d10863b），重写会同时拉高新增和删除；
- 行数含自动生成资源的增删，仅作参考。

### 3.2 采用的度量维度

| 维度 | 度量方式 |
| ---- | -------- |
| 代码贡献 | 提交数、变更行数、涉及模块 |
| 工程协作 | 本仓库的 issue、PR、代码评审（自 2026-11-05 起记录，见第 4 节） |
| 文档与交付物 | 文档、测试、演示视频等交付物的产出 |

### 3.3 分配结果

> 下表是依据第 2 节 git 度量与 3.1–3.2 节维度给出的**建议值**，不是代码行数的直接换算。**两名成员在 PR 评审中确认后即为最终结果**；如与协商结论不同，请直接在评审时改表。

| 成员 | 工作量占比 | 主要理由 |
| ---- | ---------- | -------- |
| 潘妍朵 | 70% | 承担识别子系统（端侧模型六轮迭代、特征工程、parity 校验与实验报告）、华为账号云同步与数据层、多账本 / 账单导入导出 / 预算 / 周期账单等主功能，以及 CI 与全部交付文档；按变更行数占 94.5%、提交数占 89.8%，且所负责模块的技术风险与实验验证成本最高 |
| 伍翰彬 | 30% | 承担桌面小组件三轮重设计与自定义主题 UI、跨进程主题一致性修复、界面缺陷修复，并负责测试验证与演示视频；按行数占 5.5%、提交数占 10.2%，但界面重写会同时拉高新增与删除（见 2.3 的 d10863b），真机验收与演示准备也不体现在 git 度量中 |

**为什么建议值不是按行数的 94.5% / 5.5%**：行数无法反映模型训练、特征设计与实验复核的投入；UI 重写使删除行数偏高，也不等于净工作量；演示视频、真机联调、代码评审与上架合规材料属于共同交付工作，未计入 git 度量。因此在行数的基础上，对非代码贡献与协作环节做了调整，建议取 70% / 30%。两位成员如对比例有异议，以协商结果为准。

复现命令（需安装 GitHub CLI）：

```bash
gh issue list --state all --assignee <用户名>
gh pr list --state all --author <用户名>
gh pr list --state all --search "reviewed-by:<用户名>"
```

## 5. 提交质量

- 约定格式 `类型(范围): 详细中文说明`，见 CONTRIBUTING；
- 大多数提交遵循该格式和单一职责粒度，关键提交附量化说明（如准确率、命中数、parity 规模）；
- **已知例外**（历史提交不改写，两人协作时强制推送有风险）：
  - 一条提交使用了 `fix(资源):` 的中英混用写法；
  - 若干提交合并了多件事，例如多账本功能与 4 个缺陷修复同一次提交、`功能(多模块)` 一次提交涉及统计页、首页汇总口径、AI 助手等多项、小组件与自定义主题合并提交（d10863b）；
- 自 2026-11-05 起，新提交严格按单一职责拆分。
