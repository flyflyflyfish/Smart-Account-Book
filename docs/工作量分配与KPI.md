## 3. 分配依据与原因

### 3.1 为什么不只看代码行数

- 识别子系统的工作包含模型训练、特征设计、实验与 parity 校验，产出体现在准确率提升和实验报告上，不完全等价于代码行数；
- UI 工作的行数受界面重写影响较大（见 2.3 中 d10863b），重写会同时拉高新增和删除；
- 行数含自动生成资源的增删，仅作参考。

### 3.2 采用的度量维度

| 维度 | 度量方式 |
| ---- | -------- |
| 代码贡献 | 提交数、变更行数、涉及模块 |
| 工程协作 | 本仓库的 issue、PR、代码评审（自 2026-11-05 起记录，见第 4 节） |
| 文档与交付物 | 文档、测试、演示视频等交付物的产出 |

### 3.3 分配结果

> 分工按**条线**划分，两条线各自端到端负责，因此占比不完全对应代码行数。下表为两名成员协商确认的结果。

| 成员 | 主责条线 | 工作量占比 |
| ---- | -------- | ---------- |
| 潘妍朵 | 智能识别与云能力（技术主线） | 65% |
| 伍翰彬 | 产品体验与交付（界面主线） | 35% |

依据：

- **技术风险权重**：识别子系统含端侧模型训练、特征设计与六轮实验复核，是产品核心卖点，单点失败会直接影响可用性，承担该部分即承担主要技术风险，其投入不完全体现为代码行数；
- **界面工作的度量失真**：伍翰彬的提交以界面重写为主（9669e00 单次 826 增 / 793 删），git 把"重写"计为高删除，净产出被明显低估；小部件与主题的工作量大量消耗在真机调试与像素级对齐上，不产生提交记录；
- **非代码交付未计入 git**：真机验收、演示视频、上架合规材料与测试补充属于共同交付工作，目前仍以 issue #5 / #6 跟踪，完成前不计入度量。

git 度量（第 2 节）如实保留，供核对口径差异；如对比例有异议，以两人重新协商的结论为准。


## 5. 提交质量

- 约定格式 `类型(范围): 详细中文说明`，见 CONTRIBUTING；
- 大多数提交遵循该格式和单一职责粒度，关键提交附量化说明（如准确率、命中数、parity 规模）；
- **已知例外**（历史提交的粒度不改写，两人协作时强制推送有风险；作者邮箱已于 2026-11-09 统一修正，见第 6 节）：
  - 一条提交使用了 `fix(资源):` 的中英混用写法；
  - 若干提交合并了多件事，例如多账本功能与 4 个缺陷修复同一次提交、`功能(多模块)` 一次提交涉及统计页、首页汇总口径、AI 助手等多项、小组件与自定义主题合并提交（9669e00）；
- 自 2026-11-05 起，新提交严格按单一职责拆分。
